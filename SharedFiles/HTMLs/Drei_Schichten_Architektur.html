Einordnung

Wo kommt das her?

+

Ihr kennt bereits die sieben klassischen Probleme dateibasierter Datenhaltung: Redundanz, schwieriger Zugriff, isolierte Daten, Integritätsprobleme, Nebenläufigkeit, Sicherheit, kein Absturzschutz. Diese Probleme entstehen vor allem dann, wenn Anwendung und Datenspeicherung eng miteinander verdrahtet sind.

Genau diese Trennung, wer sieht was und wo die Daten wirklich liegen, wurde in den 1970er Jahren als offizielles Modell festgehalten: die ANSI/SPARC 3-Schichten-Architektur (auch 3-Ebenen-Modell genannt). Sie beschreibt eine Datenbank aus drei Blickwinkeln, die übereinander liegen.

Wenn Datenverwaltung zentral und in drei sauber getrennte Ebenen organisiert ist, verschwinden viele der Dateisystem-Probleme automatisch, oder werden zumindest zur Aufgabe der Datenbank statt jedes einzelnen Programms.

Das Modell

Die drei Ebenen im Überblick

+

Die drei Ebenen liegen gedanklich übereinander, von außen/oben (Nutzer-Sicht) nach innen/unten (physische Speicherung):

Die 3 Ebenen als Stapel
Externe Ebene Sicht des einzelnen Nutzers oder der Anwendung
↓ AnfrageErgebnis ↑
Konzeptionelle Ebene Gesamtstruktur: alle Tabellen, Beziehungen, Regeln
↓ AnfrageErgebnis ↑
Interne Ebene Physische Speicherung: Dateiformate, Indexe, Speicherorte

Eine Anfrage wandert von oben nach unten, das Ergebnis läuft denselben Weg zurück nach oben.

EbeneFrage, die sie beantwortetBeispiel
Extern (oben)Was sieht dieser Nutzer?Kundin sieht: Datum, Artikel, Preis
Konzeptionell (Mitte)Wie ist die Datenbank insgesamt strukturiert?Tabellen KUNDEN, BESTELLUNGEN, ARTIKEL + Beziehungen
Intern (unten)Wie liegen die Daten physisch?Indexe, Dateiblöcke, Speicherort auf der SSD
Ebene 1 von 3

Die externe Ebene

+

Das ist das, was der einzelne Nutzer oder eine Anwendung sieht. Ein Vertriebsmitarbeiter sieht zum Beispiel nur Kundendaten und Bestellungen, aber keine internen Lagerbestandsdaten. Verschiedene Nutzer können ganz unterschiedliche „Sichten" auf dieselbe Datenbank haben, je nachdem, was sie für ihre Arbeit brauchen.

Der Fachbegriff für eine solche externe Sicht ist View. In SQL erstellt man später mit CREATE VIEW genau so eine eingeschränkte Sicht auf Daten.

Ebene 2 von 3

Die konzeptionelle Ebene

+

Das ist die Gesamtstruktur der Datenbank: alle Tabellen, alle Beziehungen, alle Regeln, unabhängig davon, wie einzelne Nutzer sie später sehen. Man kann sie sich als die „eine Wahrheit" über die Struktur der Daten vorstellen, auf der alle externen Sichten aufbauen.

Ebene 3 von 3

Die interne Ebene

+

Das beschreibt, wie die Daten tatsächlich auf der Festplatte oder SSD gespeichert sind: Dateiformate, Indexe, Speicherorte. Das interessiert normalerweise nur die Datenbank-Software selbst, nicht den Endnutzer.

Der entscheidende Vorteil

Datenunabhängigkeit

+

Weil die drei Ebenen sauber getrennt sind, kann man eine Ebene ändern, ohne die anderen anzufassen:

Physische Datenunabhängigkeit

Die Datenbank-Administratorin kann die interne Speicherung optimieren, zum Beispiel einen neuen Index anlegen oder Daten auf eine schnellere Festplatte verschieben, ohne dass sich für die Anwendung oder den Nutzer irgendetwas ändert.

Logische Datenunabhängigkeit

Man kann die konzeptionelle Struktur erweitern, zum Beispiel eine neue Spalte hinzufügen, ohne dass alle bestehenden Anwendungen kaputtgehen, solange ihre Sicht unverändert bleibt.

Der Umwandlungsschritt zwischen zwei Ebenen heißt Mapping (externes/logisches Mapping, konzeptionelles/internes Mapping). Für den Anfang reicht es, das Prinzip zu verstehen, ohne den Fachbegriff auswendig zu können.

Beispiel

Eine Abfrage durch alle drei Ebenen

+

Stellt euch ein Online-Bestellsystem vor. Eine Kundin klickt auf „Meine letzten Bestellungen".

Der Weg der Abfrage
1 · EXTERN

Die App zeigt der Kundin eine einfache Liste: Datum, Artikel, Preis. Das ist ihre Sicht, sie sieht keine internen Felder wie Lagerort oder Lieferanten-ID.

→
2 · KONZEPTIONELL

Die Anfrage wird übersetzt: „Bestellungen" besteht eigentlich aus mehreren verknüpften Tabellen, KUNDEN, BESTELLUNGEN und ARTIKEL, verbunden über Schlüssel (das kennt ihr bald als JOIN).

→
3 · INTERN

Das DBMS entscheidet, wie es die Daten physisch findet, zum Beispiel über einen Index auf die Kunden-ID, statt die komplette Tabelle zu durchsuchen. Es liest die passenden Datenblöcke von der Festplatte.

↻

Das Ergebnis läuft denselben Weg zurück: intern → konzeptionell → extern, wo es wieder in die einfache Listenform gebracht wird, die die Kundin am Ende sieht.

Der Clou: Die Kundin merkt von alledem nichts. Tauscht die Firma morgen die Festplatten aus oder baut einen neuen Index ein, ändert sich an ihrer App-Ansicht gar nichts, genau das ist Datenunabhängigkeit in der Praxis.

Gut zu wissen

Hintergrundwissen

+
  • Das Modell heißt offiziell ANSI/SPARC-Architektur, veröffentlicht 1975 von einer ANSI-Arbeitsgruppe (Study Group on Data Base Management Systems, kurz SPARC). Es ist bis heute die Standard-Erklärung für DBMS-Architektur in fast jedem Lehrbuch.
  • Der Fachbegriff für die externe Sicht ist View, in SQL später erzeugt mit CREATE VIEW.
  • Die Umwandlung zwischen den Ebenen heißt Mapping (externes/logisches Mapping, konzeptionelles/internes Mapping).
Nicht verwechseln: Die 3-Schichten-Architektur (ANSI/SPARC, über Daten-Sichten) ist etwas anderes als die „3-Tier-Architektur" aus der Softwareentwicklung (Präsentationsschicht / Anwendungslogik / Datenbank als Server). Das sind zwei verschiedene, ähnlich benannte Konzepte.

Zusammenfassung

Was ihr mitnehmen solltet

+
  • Die ANSI/SPARC 3-Schichten-Architektur beschreibt eine Datenbank aus drei Ebenen: extern, konzeptionell, intern.
  • Extern zeigt die Sicht des Nutzers, konzeptionell die Gesamtstruktur, intern die physische Speicherung.
  • Diese Trennung ermöglicht Datenunabhängigkeit, physisch und logisch, den zentralen Vorteil des Modells.
  • Eine Abfrage durchläuft alle drei Ebenen hin und wieder zurück, ohne dass der Nutzer davon etwas merkt.
